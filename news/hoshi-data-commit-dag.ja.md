二つのノードが一時的に通信できなくなり、その間にも両方が書き込みを受け付けたとします。通信が戻ったとき、どちらのデータを残すべきでしょうか。

交換するものが「現在の値」だけなら、すぐにどちらかを選ぶ問題になります。どちらが新しく、どのノードを正とし、もう一方の変更を捨てるのか。しかし、「それぞれが何をしたか」と「アプリケーションに最終的に何を見せるか」は、異なる問いです。

hoshi-data の操作ログは、この区別から出発します。**ノードは不変の事実を複製し、明示的な規則から現在の状態を導きます。** その事実を保持する構造が、コミットと因果関係からなる有向非巡回グラフ、Commit DAG です。

本稿は 2026 年 9 月 12 日時点の設計を説明します。ここで述べる保証は、操作ログに接続され、対応するポリシーを採用したデータセットに限られます。サービス内のすべてのデータが同じ複製能力を持つわけではありません。また、本稿は性能評価や形式的な正しさの証明ではありません。

## 1. Git をデータベースにするわけではない

hoshi-data は Hoshivel の内部データサービスです。アプリケーションは意味の定義された操作を通してデータを読み書きし、永続化とクエリは引き続き PostgreSQL が担います。Commit DAG がトランザクション、インデックス、クエリ機能を置き換えるわけではありません。

変わるのは、複製の基本単位です。操作ログに接続されたデータセットでは、現在の行だけでなく、その状態を生んだ操作も保持します。各コミットには、一緒に受理された操作と、その作成者がすでに観測していた履歴を記録します。アプリケーションが参照するデータは、コミットから導かれる投影、つまり materialized state です。

二つの層として捉えられます。

```text
不変のコミット集合 + バージョン付きの規則
                  |
                  v
             決定的な再実行
                  |
                  v
          クエリ可能なデータ投影
```

Git と似ているのは、内容アドレス、不変の履歴、親コミットとの関係です。Git コマンドで業務データを保存するという意味ではありません。任意の SQL をコミットに包めば自動的に複数ノードで書き込めるわけでもなく、各操作に再実行可能な意味と衝突の扱いが必要です。

## 2. コミットが記録するもの

概念上、コミットは次のことを説明できなければなりません。誰が生成し、その生成元の履歴のどこに位置するか。どの先行コミットに依存し、どの操作を含み、その操作をどのバージョンの規則で解釈するか。

hoshi-data は生成元の連番、親コミット集合、ハイブリッド論理時計（HLC）、スキーマとポリシーのバージョン、順序を持つ操作列を保存します。**ここで説明しているのはデータモデルであり、公開された通信フォーマットではありません。**

コミットの識別子は、正規化した内容から計算します。同じコミットが異なる経路で届いても識別子は同じなので、重複を排除できます。意味を持つ内容が変われば、別のコミットになります。親は集合なので符号化順序を固定します。一方、操作は列であり、二つの操作を入れ替えると意味が変わり得るため、無条件には並べ替えません。

不変性にも具体的な意味があります。過去のコミットの親を書き換えたり、他のノードの履歴を都合のよい形に rebase したりしません。過去の操作を訂正するときは新しい操作を追加します。古い事実は残し、履歴全体の解釈によって現在の状態を求めます。

ただし、内容アドレスは業務上の正しさを保証しません。一つのリクエストから別々のコミットが二つ作られた場合、そのハッシュだけでは、業務操作として一回と数えるべきか判断できません。操作レベルの冪等性は別に必要です。

## 3. DAG が保持するのは到着順ではなく因果関係

A を共有済みの履歴とします。二つのノードがそれぞれ A を観測して B と C を作り、その後、B と C の両方を観測したノードが D を作ったとします。

```text
       B
      / \
A ---     --- D
      \ /
       C

B.parents = {A}
C.parents = {A}
D.parents = {B, C}
```

図は左から右へ、先行する事実から後続の操作を表します。実際の親参照は逆向きで、子コミットから親コミットを指します。

B と C は互いに依存しないため、並行した操作です。これは物理的に同時刻に発生したという意味でも、必ず衝突するという意味でもありません。この履歴には、一方が他方を先に観測したという関係がないという意味です。D は両方の後に解釈する必要があります。

したがって、ネットワーク上の到着順を操作順にしてはいけません。一方のノードが C を先に受け取り、他方が B を先に受け取っても、投影が永久に異なるべきではありません。hoshi-data はまず因果関係に従ってトポロジカルソートし、その時点で処理可能な並行コミットを HLC、生成元識別子、コミット識別子で決定的に順序付けます。実装には、挿入順に依存する通常のキューではなく、優先度付きキューを使います。

HLC は再現可能な順序を作るために使います。**現実世界でどちらが後に起きたかを証明するものではなく、親参照が表す因果関係の代わりでもありません。**

重要なのは、この全順序が各ノードの「既知のコミット集合」から計算される点です。すべてのノードが実行前に合意した、永久に変わらないグローバルなログ位置ではありません。遅れて到着する並行コミットによって、まだ確定していない結果が変わる可能性は残ります。

## 4. 同じ事実から同じ状態を導く

DAG があるだけでは、任意のプログラムが収束するようにはなりません。核心は、操作を順に解釈して状態を導く reducer の契約です。

より正確には、次のように表せます。

```text
S = Reduce(B, CanonicalOrder(C), R)

B：同じ有効な初期状態または checkpoint
C：同じ有効な、依存関係が揃ったコミット集合
R：同じ意味を持つバージョン付きの規則
S：得られる投影
```

C が等しいだけでは不十分で、B と R も一致する必要があります。親コミットの不足や生成元の連番の欠落を、情報が揃ったものとして扱うことはできません。未知のポリシーバージョンを、利用可能な「近い」バージョンに置き換えて実行することもできません。

この契約は reducer が参照できる情報を制限します。ローカルの現在時刻、パケットの到着順、データベースの偶然の行順、言語処理系の map の走査順によって答えが変わってはいけません。数値と符号化についても、表現の違いが曖昧さを生まないようにする必要があります。

バージョンは契約の一部ですが、**番号を記録するだけで任意の混在バージョンや自動更新に対応できるわけではありません**。過去の規則を保持し、解釈できない履歴は拒否する必要があります。互換性の設計と検証は、バージョン欄では代替できません。

## 5. 同期は不足している事実を探す

同期とは、最新の値を送るだけではありません。互いに不足しているコミットを見つけ、通信できるようになったら繰り返し補います。この比較と修復の過程を、一般に anti-entropy と呼びます。

生成元の連番が役立つのはここです。ある生成元の 4 番と 6 番が届き、5 番がまだなら、連続した進捗は 4 までです。「最大で 6 番を見た」ことを同期完了の進捗にすると、欠落を隠してしまいます。親参照も依存関係の確認に使います。子が届いたからといって、必要な履歴が揃う前に投影してよいわけではありません。

混同しやすい二種類の frontier も区別します。親コミット集合は、作成者が観測していた DAG の先端を表します。同期の進捗は、生成元ごとの最大連続番号を記録します。前者は因果関係を、後者は欠落の発見を扱うもので、一つの最大タイムスタンプでは両方を代替できません。

重複配信はコミット識別子で排除でき、不足する依存関係は取得を待てます。しかし、生成元による連番の再利用、不正な内容、生成元の検証失敗は、通常の並行書き込みとしてマージして済ませられるものではありません。

内容と生成元を検証していても、それだけで完全な Byzantine 障害耐性を持つとは言えません。改ざんの検出、どの生成元の事実を受理するかという判断、任意に悪意あるノードへの耐性は、別々の問題です。

## 6. 必要な協調は操作の意味で決まる

このモデルで最も混同しやすいのは、「全員が最終的に同じ答えを得る」ことと「その答えが正当である」ことです。

残り一枠の資源を考えます。二つのノードが別々の利用者にその枠を約束し、後から決定的な規則で一人を選べば、状態は収束します。しかし、すでに二人にした約束が正しかったことにはなりません。これはアプリケーションの不変条件の問題であり、並べ方を変えて解決するものではありません。

そこで hoshi-data は操作の種類を区別します。

- **可換または単調な操作**：対応するポリシーの保証の下では、並行する新しい事実が確認済みの効果を覆しません。すべての書き込みで先にグローバルな順序を取得する必要はありません。
- **決定的に競合解決できる操作**：現在の勝者は計算できますが、結果が暫定である場合があります。勝者を選べることと、後から覆らないことは異なります。
- **上限または排他条件を持つ操作**：事前に配分した権利、つまり escrow を使うか、必要な協調の証拠を取得します。どこでも無条件に書き込みを受け付けるわけではありません。

架空の容量 10 の資源なら、二つのノードに使用権を 6 と 4 に分けられます。各ノードが自分の権利だけを消費すれば、通信できない間も合計は 10 を超えません。その代わり、4 を持つノードは、相手に余裕があると推測しても 5 の消費を承認できません。

権利の移転も、片方で引いてもう片方で足すだけでは不十分です。モデルでは、移転中の権利を受信側の未受領領域に置き、受信側が受領してから使用可能にします。次を維持します。

```text
使用可能な権利の合計 + 移転中の権利の合計 + 消費済み量 = 総容量
```

このように分割できない排他条件には、引き続き協調が必要です。あるキーに必要な quorum や証拠を得ても、データベース全体やデータセットをまたぐ操作に、グローバルな直列化可能性が自動的に与えられるわけではありません。

目標は協調の排除ではなく、**意味上必要な境界に協調を限定すること**です。現在の境界は明示的な操作ポリシーとして実装されており、任意の業務コードを自動解析して導かれるものではありません。

## 7. 書き込み済み、収束済み、確定済みは異なる

あるコミットがローカルで永続化されても、すべてのノードが保持しているとは限りません。既知のコミットから同じ投影が得られても、未観測の並行コミットが結果を変えないとは限りません。

そのため hoshi-data は、操作結果の finality をモデルに含めます。結果には、確定済み（finalized）、暫定（provisional）、後の解釈によって置き換えられた状態（superseded）があります。確定は対応するポリシーの下での結果保証であり、すべてのレプリカや遠隔バックアップへの永続化完了を意味しません。

特に重要なのが外部への副作用です。投影は再構築できますが、送信済みのメールや引き渡し済みの資源は、データベースの再実行だけでは取り戻せません。Outbox はイベントの確定状態を扱い、受信側も暫定結果を受け入れるか明示的に判断する必要があります。一度のローカル append の成功だけでは、不可逆な副作用を実行する十分な根拠になりません。

同様に、コミットの重複排除はエンドツーエンドの exactly-once を意味しません。サービス間のリトライと outbox の配信には、それぞれ冪等性の処理が必要です。一部分の重複排除だけでは、経路全体の保証にはなりません。

## 8. 投影を再構築できても履歴は自由に捨てられない

操作ログがあると、現在の状態だけがデータを説明する手がかりではなくなります。投影を検査・再構築するとき、特定のノードの現在の行を正解とするのではなく、同じ事実と規則から導き直せます。

ただし、データベースへの接続にはトランザクション境界が必要です。関連するコミット、投影、冪等性の記録は、書き込み経路に応じたローカルトランザクションに含める必要があります。一つのコミットが、もともと原子性のないデータベース境界を自由にまたげるわけではありません。汎用のデータベース間 two-phase commit ではありません。

Checkpoint は、ある frontier での投影、連続した進捗、バージョン情報を保存し、対応する履歴を照合できるダイジェストを提供します。**Checkpoint があっても、それ以前のコミットをすべて安全に削除できるわけではありません。** ダイジェストの一致は内容の整合性に関する一部の問いに答えるだけです。生成元への信頼、依存関係の完全性、長期間オフラインだったノードがその履歴を必要としないことまでは証明しません。

現在の新規メンバーの参加経路も、外部スナップショットをそのままローカルの正として取り込みません。Checkpoint を照合先とし、履歴を取得して自ら再実行し、目標の投影と比較してから読み取り可能な状態になります。書き込みの許可は別の明示的な段階です。スナップショットを取得すれば全履歴を省略できる能力とは異なります。

履歴の安全な削除、checkpoint だけからの起動、検証可能な因果依存関係の維持は、それぞれ解決すべき別の課題です。

## 9. 検証すべきことと、主張していないこと

通常時に書き込みが成功するだけでは、この設計を検証したことになりません。モデル層では、同じ有効なコミット集合に対し、配信順を変え、重複を加え、依存関係が揃ってから再実行し、投影が一致するか確認する必要があります。欠落、未知のポリシー、不正な生成元に対しては、推測せず拒否することも確認します。

永続化とネットワークを接続した後には、ネットワーク分断、プロセスの中断と再起動、新規メンバーの追従、外部への副作用も検証対象になります。純粋な reducer の性質が成立しても、トランザクションとの接続、同期プロトコル、復旧処理に誤りがないとは言えません。

これらは保証の範囲も定めます。収束には、同じ有効な事実、同じ規則、そして不足するデータを最終的に取得できることが必要です。すべてのコピーから失われたコミットを DAG が復元することはできません。複製は独立したバックアップの代わりにはなりません。ノードをまたぐ読み取りの因果要件にも明示的な読み取り条件が必要で、DAG が存在するだけですべての読み取りが直ちに一致するわけではありません。

本稿では、合意ベースの複製より高速だとは主張せず、システム全体の形式的な正しさも証明していません。レイテンシー、スループット、履歴の増大、再実行コスト、復旧時間は、保証を比較できるワークロードで測定する必要があります。

## 10. 工学的な実装から研究課題へ

内容アドレス、因果 DAG、収束するデータ型には、重要な先行研究があります。[Merkle-CRDTs][merkle] は CRDT の転送・永続化層としての Merkle-DAG を論じています。[Coordination Avoidance in Database Systems][coordination] は invariant confluence を用い、協調なしの実行とマージでも維持できるアプリケーションの不変条件を分析します。[Highly Available Transactions][hat] は高可用性と各種トランザクション保証の境界を扱います。

hoshi-data の工学的な価値は、DAG を発明したという主張ではありません。操作の意味、確定状態、永続化、障害復旧を、一つの検査可能な契約にまとめる点にあります。似た構造を使うだけで、先行研究の定理をすべて引き継げるわけでもありません。

今後の研究として特に関心があるのは二つの問いです。第一に、規則やスキーマが進化するとき、明示的な互換性条件の下で過去の意味をどう維持し、非互換なノードが黙って再解釈せず安全に拒否できるようにするか。第二に、履歴を削除した後でも、遅れて参加したノードや長期オフラインだったノードが依存関係を検証し、結果を再構築し、必要な監査可能性を保てるようにするにはどうするか。

これらは研究の方向性であり、完成済み機能の発表ではありません。論文としての貢献には、明確な問題モデル、先行研究との差分、正しさの論証、再現可能な実験が必要です。評価でも、同等の保証を持つ基準との比較を行い、同期通信量、再実行と保存のコスト、障害後の収束時間、協調が必要な操作の割合を測るべきです。有利なスループットのグラフ一枚では十分ではありません。

現在の hoshi-data の原則は単純です。**「データが今どのような形をしているか」だけを、私たちの知るすべてにしないこと。その状態を生んだ事実を残せば、並行処理、障害、変化を経た後も、説明できる答えを計算し直せます。**
