两个节点暂时无法通讯，却都收到了写入。连线恢复后，我们究竟应该保留哪一份资料？

若交换的只是「现在的值」，这个问题很快就会变成选边：哪一份较新、哪个节点说了算，以及另一边的修改是否必须丢弃。但「各自做了什么」与「最后应该看到什么」，其实是两个不同的问题。

hoshi-data 的操作日志从这个区分出发：**节点复写不可变的事实，再以明确的规则推导目前的状态。** 承载这些事实的结构，是 Commit DAG——一张由提交及其因果关系组成的有向无环图。

本文记录截至 2026 年 9 月 12 日的工程设计。所述保证只适用于已整合操作日志、采用相应政策的资料集；不是整个服务的所有资料都已具有相同的复写能力，也不是一份效能或形式化证明报告。

## 1. 不是把 Git 当资料库

hoshi-data 是 Hoshivel 的内部资料服务。应用透过具语意的操作介面读写资料，持久化与查询仍由 PostgreSQL 承担；Commit DAG 并没有取代资料库的交易、索引或查询能力。

改变的是复写的基本单位。对整合日志的资料集，我们不只保留目前的资料列，也保留导致状态改变的操作。每次提交描述一组一起被接受的操作，以及作者当时已经看见的历史。供应用查询的资料，则是由这些提交推导出的投影，也就是 materialized state。

可以把它理解成两个层次：

```text
不可变提交集合 + 版本化规则
              |
              v
         确定性重播
              |
              v
       可查询的资料投影
```

这与 Git 的相似之处，在于内容定址、不可变历史与父提交关系，而不是使用 Git 指令储存业务资料。它也不是把任意 SQL 包进提交后自动取得多主写入能力：每种操作都必须先有可以重播、可以解释冲突的语意。

## 2. 一个 commit 记住什么

在概念上，一个提交需要回答：谁产生它、它在该来源历史中的位置、它依赖哪些已知提交、它包含哪些操作，以及那些操作应按哪一版规则解读。

hoshi-data 为此储存来源序号、父提交集合、混合逻辑时钟（HLC）、结构与政策版本，以及有顺序的操作内容。**这里描述的是资料模型，不是公开线路格式。**

提交的识别符由其规范化内容计算。同一份提交沿不同路径抵达，仍会得到相同的识别符，因此可以去重；更改有意义的内容，就不再是同一份提交。父提交是集合，编码顺序必须固定；操作却是序列，交换两个操作的位置可能改变语意，不能任意排序。

「不可变」也有很直接的含义：不重写旧提交的父关系，不把另一边的历史 rebase 成自己喜欢的形状。需要修正先前操作时，追加新的操作；旧事实留在历史里，新的状态由完整历史重新解释。

不过，内容定址保证的不是业务正确性。同一个请求若被做成两份不同提交，不能单靠 hash 判断它们是否应算同一次业务操作；那仍需要操作层的幂等设计。

## 3. DAG 保留的是因果，不是抵达时间

假设 A 是共同历史，两个节点各自在看过 A 之后产生 B 与 C。稍后，某个节点看过 B、C，再产生 D：

```text
       B
      / \
A ---     --- D
      \ /
       C

B.parents = {A}
C.parents = {A}
D.parents = {B, C}
```

图中由左向右表示「先前事实到后续操作」；实际父引用则由子提交指回父提交。

B 与 C 没有互相依赖，所以它们是并行操作。并行不代表发生在完全相同的物理时间，也不必然构成冲突；它只表示这份历史没有记录其中一个先看见另一个。D 则必须在两者之后解读。

因此，不能把网路抵达顺序当成操作顺序。某个节点先收到 C，另一个先收到 B，并不应导致永久不同的投影。hoshi-data 先做因果拓扑排序，再对当下可处理的并行提交，以 HLC、来源识别与提交识别符作确定性的决胜排序。实作使用带优先伫列的拓扑排序，而不是依插入顺序取出的普通伫列。

HLC 在这里参与可重现的排序，**不证明真实世界中哪个操作比较晚，也不取代父提交所记录的因果关系**。

尤其重要的是：这个全序是各节点对「已知提交集合」算出的顺序，不是所有节点事先以共识承诺、永远不再变动的全域日志位置。晚到的并行提交仍可能改变尚未定案的结果。

## 4. 同样的事实，必须得到同样的状态

DAG 本身不会替任意程式提供收敛性。真正需要守住的是 reducer，也就是把操作逐一解读成状态的规则。

较完整的表达是：

```text
S = Reduce(B, CanonicalOrder(C), R)

B：相同且有效的起始状态或 checkpoint
C：相同、有效且依赖完整的提交集合
R：具有相同语意的版本化规则
S：推导出的投影
```

只有 B、C、R 都相同，才能要求两个节点得到相同的 S。缺少父提交或来源序号有缺口时，不能假装资讯完整；不知道某个政策版本时，也不能改用「最接近」的版本继续执行。

这也限制了 reducer 可以读取的资讯。它不能因本机现在几点、网路先送来哪一包、资料库刚好回传哪个行序，或程式语言的 map 迭代顺序，而产生不同答案。操作的数值与编码，也必须避免不同表示方式带来的歧义。

版本栏位是这个契约的一部分，但**记下版本号，不等于已经解决任意版本混跑或自动升级**。历史规则需要被保留；无法解读的历史必须拒绝处理。跨版本演进仍然需要相容性设计与验证，不能由一个栏位代替。

## 5. 同步的工作是找出缺少的事实

节点同步不只是推送最新值，也要辨认对方缺了哪些提交，并在通讯恢复后反复补齐。这类反复比对与修补的过程，通常称为 anti-entropy。

来源序号在这里尤其有用。若某个来源的第 4 与第 6 份提交已抵达，第 5 份尚未抵达，连续进度仍只能到 4，不能用「见过的最大序号是 6」宣称同步完成。父提交引用则提供另一种依赖检查：即使收到子提交，也必须先取得它需要的历史，才能安全投影。

这里有两种容易混淆的 frontier：父提交集合描述作者已看见的 DAG 前沿；同步进度则按来源记录最高连续序号。前者回答因果关系，后者帮助找出缺口，不能只拿一个最大时间戳同时代替两者。

重复投递可以由提交识别符去重，缺少依赖可以等待补齐；但来源重用序号、内容不合法或来源验证失败，不是普通的并行写入，不能「合并一下」就算了。

即使有内容与来源验证，也不能因此宣称具备完整的 Byzantine 容错。辨识窜改、接受哪些来源的事实，以及容忍任意恶意节点，是不同层次的问题。

## 6. 需要多少协调，由操作语意决定

最容易误解这个模型的地方，是把「所有节点最后会得到同一个答案」当成「那个答案一定合法」。

假设只有一个名额。两个节点各自把它承诺给不同的人，最后再确定性地选出一个赢家，确实可以收敛；但先前已经对两个人作出的承诺，不会因此变成正确。这是应用不变式的问题，不是换一种排序方式就能解决。

hoshi-data 因此区分不同的操作类别：

- **可交换或单调的操作**：在其政策保证下，新的并行事实不会推翻已确认的效果，不必为每次写入先取得全域顺序。
- **可确定性解冲突的操作**：可以计算目前胜出的值，但结果仍可能是暂定的；「能选出赢家」不代表「已不可推翻」。
- **受额度或排他条件约束的操作**：使用预先分配的权利（escrow），或取得所需的协调证据，而不是无条件在各处接受写入。

例如，总量为 10 的虚构资源，可以先把 6 与 4 的使用权分配给两个节点。各自只消耗持有的权利，即使暂时失联，也不会合计消耗超过 10。代价是持有 4 的节点不能自行批准消耗 5，即使它猜测另一边还有剩余。

权利转移也不是在两端各加减一次便算完成。模型把转移中的权利放在接收方的待领取区，接收方领取后才能使用，维持：

```text
可用权利总和 + 转移中权利总和 + 已消耗量 = 总额度
```

无法用这种方式拆分的排他条件，仍需协调。取得某个键所需的 quorum 或证据，不代表整个资料库、所有跨资料集操作都自动具有全域可序列化保证。

因此，我们追求的不是「消灭协调」，而是**把协调留在确实需要它的语意边界**。目前这些边界由明确的操作政策实作，不是自动分析任意业务程式得出的结论。

## 7. 已写入、已收敛、已定案，是三件事

一份提交已在本机持久化，不代表所有节点都已持有它；所有已知提交算出了相同的投影，也不代表未见过的并行提交再也不会改变结果。

hoshi-data 因此把操作结果的 finality 纳入模型。结果可能已定案（finalized）、仍属暂定（provisional），或已被后续解读取代（superseded）。其中「定案」描述的是相应政策下的结果保证，不是宣告每个副本或异地备份都已完成持久化。

这个区分在外部副作用上尤其重要。投影可以重建，已寄出的邮件或已交付的资源却不能靠重播资料库自动收回。Outbox 必须知道事件的定案状态，接收端也必须明确决定能否接受暂定结果；不能把一次本地 append 的成功，直接当成执行不可逆副作用的充分条件。

同样地，提交去重不等于端到端 exactly-once。跨服务重试与 outbox 投递仍需要各自的幂等处理；整条链路的保证，不能由其中一段的去重能力代为宣告。

## 8. 投影可以重建，历史却不能随意丢弃

操作日志让目前状态不再是唯一能解释资料的地方。当投影需要核对或重建时，可以从相同的事实与规则重新推导，而不是直接挑某个节点当下的资料列作为答案。

不过，把这件事接到资料库仍需交易边界。相关提交、投影及幂等纪录，必须按写入路径放在相应的本地交易中；一份提交的操作不能任意跨越原本不具原子性的资料库边界。这不是通用的跨资料库 two-phase commit。

Checkpoint 则储存某个前沿的投影、连续进度与版本资讯，让已覆盖的历史有可核对的摘要。**有 checkpoint，仍不等于可以安全删掉所有旧提交。** 摘要相符只回答内容一致性的一部分问题，不能自行证明来源可信、依赖完整，或某个长期离线节点再也不需要那些历史。

目前的新成员加入流程，也没有把一份外来快照直接当成本机真相。它以 checkpoint 为核对目标，补齐历史，自行重播并比对目标投影，通过后才进入可读状态；允许写入是另一个明确步骤。这与「取得快照后即可略过全部历史」是不同的能力。

安全裁剪历史、直接以 checkpoint 启动，以及保留可验证的因果依赖，是需要分别完成的工程问题。

## 9. 我们要验证什么，又没有承诺什么

这套设计不能只用「正常情况下写入成功」验收。模型层需要直接检查：对同一个有效提交集合改变投递顺序、加入重复投递，或在依赖补齐后重播，是否仍得到相同投影；对缺口、未知政策与不合法来源，是否确实拒绝猜测。

接到持久化与网路后，还要验证分区、程序中止、重启、新成员追赶与外部副作用。纯 reducer 的性质成立，不代表交易接线、同步协定与还原流程就不可能出错。

这些也界定了本文的承诺：收敛需要相同且有效的事实、相同的规则，以及缺失资料最终可取得。所有副本都遗失的提交，不会由 DAG 凭空恢复；复写仍不能取代独立备份。跨节点读取的因果要求也需要额外的读取条件，不能因为存在 DAG 就假定所有读取立即一致。

我们没有在本文宣称比共识复写更快，也没有给出经形式化证明的整体正确性。延迟、吞吐量、历史增长、重播成本与恢复时间，都需要在一致性保证可比较的工作负载下实测。

## 10. 从工程系统走向研究问题

内容定址、因果 DAG 与收敛资料型别，都有重要的既有研究。[Merkle-CRDTs][merkle] 已讨论 Merkle-DAG 作为 CRDT 的传输与持久化层；[Coordination Avoidance in Database Systems][coordination] 用 invariant confluence 分析哪些应用不变式可以在无协调的执行与合并下维持；[Highly Available Transactions][hat] 则厘清高可用性与不同交易保证之间的边界。

hoshi-data 的工程价值，不在宣称发明了 DAG，而在把操作语意、定案状态、持久化与故障恢复放进同一套可检查的契约。借用相近的资料结构，也不代表自动继承那些研究的全部定理。

若要把这条路推进为研究成果，我们更关心两类具体问题。第一，规则与结构持续演进时，如何在明确的相容性条件下维持历史语意，让不相容的节点安全拒绝，而不是悄悄重解读资料。第二，裁剪历史之后，如何仍让晚加入或长期离线的节点验证依赖、重建结果，并保留必要的稽核能力。

这些是研究方向，不是已完成的功能宣告。要形成论文贡献，还需要清楚的问题模型、相对既有工作的差异、正确性论证，以及可重现的实验。比较也必须包含相同保证下的基线，量测同步流量、重播与储存成本、故障后收敛时间及必要协调的比例，而不只挑一张吞吐量图。

对现在的 hoshi-data 而言，核心原则仍然很简单：**不要让「这份资料现在长什么样子」，成为我们唯一知道的事。保留它如何形成的事实，才有机会在并行、故障与演进之后，重新算出可以解释的答案。**
